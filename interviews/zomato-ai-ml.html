QUESTION 01 Advanced RAG · LangChain

How would you build an end-to-end Retrieval-Augmented Generation (RAG) pipeline using LangChain?

Interview-ready answer

I would design a RAG system with two main workflows: an indexing pipeline that prepares knowledge for retrieval, and a query pipeline that retrieves relevant information and uses it to generate a grounded answer.

During indexing, I would collect documents from approved sources, extract their text, clean the content, split it into meaningful chunks, generate embeddings, and store those embeddings alongside the text and metadata in a vector database.

At query time, the user's question is converted into an embedding and used to retrieve relevant chunks. I would consider metadata filtering, hybrid search, and a reranker when semantic search alone does not provide sufficiently relevant results. The selected context is passed to the language model through a carefully designed prompt. The model generates an answer grounded in that context, ideally with citations or source references.

Finally, I would evaluate retrieval quality, answer relevance, factual grounding, latency, and cost. I would also handle empty retrieval results, conflicting documents, and questions that the available sources cannot answer.

Technical explanation

1. Document ingestion

Connect to the relevant data sources, extract text, preserve useful metadata, remove duplicate or corrupted content, and apply access-control rules. For example, a support knowledge base might include article IDs, product versions, and publication dates.

2. Chunking and embedding

Split documents into chunks that preserve meaning. Chunk size and overlap should be tested against the data rather than selected arbitrarily. An embedding model converts each chunk into a numerical vector that represents its semantic content.

3. Indexing and retrieval

Store vectors, chunk text, and metadata in a vector store. At query time, retrieve candidate chunks using semantic similarity. Hybrid retrieval combines semantic search with keyword-based methods, which can be useful for product names, IDs, and exact terminology.

4. Reranking and generation

A reranker can reorder retrieved candidates according to their relevance to the question. The final context is passed to the LLM with instructions to use the provided evidence, distinguish uncertainty, and avoid inventing unsupported facts.

5. Evaluation and monitoring

  • Retrieval: Recall@k, Precision@k, and ranking measures such as MRR or NDCG.
  • Generation: Answer correctness, relevance, groundedness, and citation accuracy.
  • Operations: Latency, token usage, cost, failures, and retrieval coverage.

LangChain can connect document loaders, text splitters, embedding models, retrievers, vector stores, and chat models. I would keep these components modular so that they can be changed and evaluated independently.

Key takeaway

RAG quality depends on both retrieval and generation. A powerful LLM cannot reliably compensate for missing, irrelevant, or incorrect retrieved context.

QUESTION 02 Intermediate NLP · Embeddings

What is the difference between BERT embeddings and Word2Vec embeddings?

Interview-ready answer

Word2Vec is a method for learning word representations from surrounding words. In its standard form, each word has a fixed vector, so the word has the same representation regardless of the sentence in which it appears.

BERT is a Transformer-based language model that generates contextual representations. Its representation of a word depends on the surrounding tokens, allowing it to distinguish different meanings of the same word in different sentences.

For example, Word2Vec typically gives the word "bank" one learned vector, whether the sentence discusses a financial institution or a riverbank. BERT can generate different contextual representations for "bank" in "I deposited money at the bank" and "We sat beside the river bank."

Word2Vec is comparatively lightweight and useful for simpler embedding tasks. BERT is generally more computationally expensive but is well suited to contextual NLP tasks such as classification, named entity recognition, and question answering.

Technical explanation

Word2Vec

  • Learns dense word vectors using objectives such as Continuous Bag of Words (CBOW) and Skip-gram.
  • Uses local word-context relationships during training.
  • Standard word vectors are static after training.
  • Does not naturally produce a different word vector for each sentence context.
  • Can be relatively efficient for applications that need simple word representations.

BERT

  • Uses a Transformer encoder with self-attention.
  • Was originally pretrained using objectives including masked language modelling.
  • Produces contextual token representations based on surrounding text.
  • Uses subword tokenization, so a word may correspond to multiple tokens.
  • Can be fine-tuned for specific tasks or used to create embeddings, depending on the model and pooling strategy.

Important practical distinction

BERT's contextual token representations are not automatically the best sentence embeddings for every similarity-search task. For semantic search, a model trained specifically for sentence or text embeddings may perform better. The correct choice should be based on the task, domain, evaluation data, compute budget, and latency requirements.

Key takeaway

Word2Vec generally provides static word vectors; BERT provides context-dependent token representations. For production retrieval, compare models on your actual search and relevance benchmarks.

QUESTION 03 Advanced Tokenization · NLP evaluation

How can excessive tokenization affect sentiment analysis and Named Entity Recognition (NER)?

Interview-ready answer

Excessive tokenization occurs when a tokenizer splits words or entities into many small subword pieces. Subword tokenization is useful for handling rare and unseen words, but excessive fragmentation can make important information harder to process.

In sentiment analysis, splitting slang, product names, abbreviations, or domain-specific expressions into unfamiliar pieces may make sentiment-bearing phrases harder to represent correctly. In NER, a person, company, or product name may span several subword tokens, which can complicate the mapping between token-level predictions and the original entity span.

I would inspect tokenization on representative examples, measure fragmentation rates, and evaluate performance by category. Possible improvements include using a suitable tokenizer-model combination, aligning subword labels correctly, normalizing noisy text carefully, and fine-tuning on representative domain data.

Technical explanation

Impact on sentiment analysis

Consider a review containing an unfamiliar product name, slang, elongated words, or an expression such as "not at all good." If tokenization fragments these expressions unusually, the model may struggle to learn reliable associations. However, fragmentation alone does not prove that a prediction will be wrong; model training and context also matter.

Impact on NER

Suppose the text contains a company name represented by three subword tokens. A token-classification model may predict labels for each subword, while the desired output is one entity span in the original text. Incorrect label alignment or span reconstruction can cause entities to be split, truncated, or assigned incorrect boundaries.

How I would investigate the problem

  1. Collect examples where sentiment or entity predictions are incorrect.
  2. Inspect the tokenized output for rare names, slang, abbreviations, multilingual text, and misspellings.
  3. Measure average tokens per word and the fragmentation rate for relevant categories.
  4. For NER, check whether training labels align correctly with subword tokens and whether predicted spans map back to the original text.
  5. Compare model performance across examples with low and high fragmentation.
  6. Test alternative tokenizers or models and fine-tune on representative examples.

Metrics to consider

  • Sentiment analysis: Macro-F1, per-class precision and recall, and confusion matrices.
  • NER: Entity-level precision, recall, and F1, with the evaluation matching the intended span-level output.
  • Operational checks: Sequence length, truncation rate, inference latency, and memory usage.

I would not automatically modify a pretrained model's tokenizer because its vocabulary and token IDs are coupled to the model's learned parameters. Changing the tokenizer may require additional embedding training and careful model adaptation.

Key takeaway

Diagnose tokenization issues using real failure examples and task-level metrics. More tokens do not automatically mean worse predictions; incorrect alignment, insufficient domain coverage, and sequence truncation are important factors to investigate.

QUESTION 04 Advanced Transformers · RoPE

What are positional embeddings, and how does Rotary Position Embedding (RoPE) work?

Interview-ready answer

A Transformer needs information about token order because self-attention does not inherently understand that one token comes before another. Positional information helps the model distinguish sequences that contain similar words in different orders.

Positional encoding approaches include learned absolute embeddings, sinusoidal encodings, and relative-position methods. RoPE, or Rotary Position Embedding, incorporates position information by rotating pairs of dimensions in the query and key representations according to each token's position.

This rotation makes the attention calculation sensitive to relative positions between tokens. RoPE is used in several modern decoder-only language models because it provides a useful way to encode sequence position within the attention mechanism.

Technical explanation

Why positional information matters

The sentences "The model evaluated the response" and "The response evaluated the model" contain similar words but express different relationships. Position information helps the attention mechanism interpret word order.

Common approaches

  • Learned absolute embeddings: Learn a position-specific vector for each supported position.
  • Sinusoidal encodings: Use fixed sine and cosine functions at different frequencies.
  • Relative-position methods: Represent relationships between token positions in attention or related components.
  • RoPE: Apply position-dependent rotations to query and key vectors.

How RoPE works conceptually

RoPE divides parts of a query or key vector into pairs of dimensions and rotates each pair by an angle determined by token position and frequency. When the rotated query and key interact through a dot product, their interaction encodes information about the relative separation between their positions.

This is particularly useful in autoregressive language models, where the model must attend to earlier tokens while generating the next token.

Does RoPE automatically solve long-context problems?

No. A model's context length also depends on its training, attention implementation, positional scaling, memory requirements, and inference configuration. Extending RoPE to longer contexts may require methods such as position interpolation or frequency-scaling approaches, followed by suitable evaluation.

For a production system, I would test quality across different sequence lengths, including long-context retrieval, positional sensitivity, and degradation near the context limit.

Key takeaway

RoPE injects positional information by rotating query and key representations. Its usefulness for long-context models depends on how the model is trained and how its positional behaviour is extended and evaluated.

QUESTION 05 Advanced Inference · Optimization

How does model quantization affect inference performance and output quality?

Interview-ready answer

Model quantization represents model parameters, and sometimes activations, using lower-precision numerical formats. For example, a model may use 8-bit or 4-bit representations instead of 16-bit or 32-bit floating-point values.

Quantization can reduce model memory requirements and sometimes improve inference speed, throughput, or energy efficiency. However, lower precision introduces approximation error that can reduce output quality, especially for sensitive tasks or aggressive quantization settings.

I would compare quantized and baseline models using representative prompts, task-specific accuracy metrics, latency, throughput, memory consumption, and cost. I would then select the quantization configuration that meets the quality and operational requirements of the application.

Technical explanation

Types of quantization

  • Post-training quantization: Converts a trained model to a lower-precision representation without full retraining. Some approaches use calibration data.
  • Quantization-aware training: Simulates quantization effects during training so the model can adapt to them.
  • Weight-only quantization: Reduces the precision of model weights while leaving some computations at higher precision.
  • Weight-and-activation quantization: Reduces precision for both weights and activations, potentially offering further efficiency benefits.

Benefits

  • Smaller model weights and reduced memory pressure.
  • Potentially larger batch sizes or the ability to serve models on less expensive hardware.
  • Possible improvements in latency, throughput, and energy use when supported by the hardware and inference software.

Risks and trade-offs

  • Reduced accuracy or reasoning quality for some tasks.
  • Potentially greater degradation with very low-bit quantization.
  • Hardware-dependent speed improvements; a smaller model is not always faster.
  • Additional engineering work to choose formats, calibration data, and kernels.

How I would evaluate it

  1. Establish a baseline using the original model and a representative evaluation dataset.
  2. Quantize the model using candidate formats such as 8-bit or 4-bit.
  3. Run the same evaluation set against each configuration.
  4. Measure quality, peak memory usage, time to first token, generation speed, and throughput.
  5. Inspect failures by task category rather than relying only on an overall average.
  6. Deploy only after validating the trade-off under realistic production load.

For an LLM application, I would also test instruction following, factuality, structured output, and tool-call reliability if those capabilities matter to the product.

Key takeaway

Quantization is a quality-efficiency trade-off, not a guaranteed speed improvement. Choose the configuration using measured results on the intended hardware and workload.

QUESTION 06 Advanced Agentic AI · Evaluation

How would you analyse and improve an Agentic AI pipeline that frequently produces incorrect results or fails to complete tasks?

Interview-ready answer

I would treat an Agentic AI system as a multi-stage workflow rather than assuming that every failure originates in the language model. An agent may need to understand a goal, plan actions, select tools, execute those tools, interpret results, maintain state, and decide when the task is complete.

I would first collect representative failure cases and trace each run through its individual stages. I would classify failures into categories such as incorrect planning, tool-selection errors, invalid arguments, tool execution failures, context loss, unsupported claims, looping, and premature termination.

Next, I would define task-specific success criteria and build an evaluation set. I would apply targeted improvements, such as stronger tool descriptions, schema validation, explicit stopping conditions, state tracking, retrieval improvements, bounded retries, or human approval for high-impact actions.

Finally, I would compare the revised pipeline against the baseline using task-completion rate, tool-call accuracy, factuality, failure rate, latency, and cost. I would release the change only if it improves the required outcomes without introducing unacceptable regressions.

Technical explanation

1. Instrument the workflow

Log the user goal, model outputs, selected tools, tool arguments, tool results, state transitions, retry counts, and final response. Redact sensitive information and enforce access controls. Without stage-level traces, it is difficult to distinguish model reasoning failures from application or infrastructure failures.

2. Classify failures

  • Planning: The agent misunderstands the goal or creates an incomplete plan.
  • Tool selection: It chooses an unsuitable tool or fails to recognize that a tool is required.
  • Tool arguments: It supplies missing, malformed, or incorrect parameters.
  • Execution: An API times out, returns an error, or produces unexpected output.
  • State and memory: The agent loses relevant information or fails to preserve results between steps.
  • Grounding: The final response contradicts tool results or introduces unsupported information.
  • Termination: It loops indefinitely, stops too early, or exceeds its step budget.

3. Build a repeatable evaluation set

Include normal requests, ambiguous instructions, missing information, API failures, invalid tool results, adversarial inputs, and tasks requiring multiple steps. Define expected outcomes and acceptable alternatives for each test.

4. Apply targeted improvements

  • Improve system instructions and tool descriptions.
  • Validate tool arguments against explicit schemas.
  • Add timeouts, bounded retries, backoff, and error handling.
  • Track task state and preserve relevant observations.
  • Use retrieval or external evidence when tasks require factual grounding.
  • Introduce step budgets, loop detection, and clear stopping criteria.
  • Require human approval for consequential or irreversible actions.

5. Evaluate the whole system

I would measure task success, partial completion, tool-call correctness, recovery from errors, unsupported claims, average number of steps, latency, and cost per successful task. I would also run regression tests because improving one stage can affect the behaviour of the complete workflow.

Agentic systems can be nondeterministic, so I would repeat tests where appropriate and report variability. For risky actions, I would test permission boundaries and confirm that untrusted tool outputs cannot override system-level instructions.

Key takeaway

Debug agents stage by stage, measure end-to-end task success, and fix the actual failure source. Better prompting alone will not solve broken tools, poor state management, or missing safeguards.
